# 요구사항

## 문서 목적

이 문서는 현재 유효한 요구사항을 정의한다. 변경 과정과 이유는 [requirements-history.md](requirements-history.md)에 누적한다. 우선순위는 `MUST`, `SHOULD`, `LATER`로 표시하며, 이는 구현 Phase와 동일한 뜻이 아니다.

## 현재 개발 범위

Phase 1의 모바일 우선 웹 골격과 메모리 전용 급여 실수령 추정기, Phase 2 Transaction Domain Foundation, Phase 3A/3B Legacy XLS Preview·확정 저장, Phase 4 중복 후보 검토, Phase 5 확정 카테고리 규칙, Phase 6A 기능별 페이지 분리, Phase 6B 계좌 거래 유형 분류, Phase 7A/7B/7C Kakao 장소 분류·진행 표시, Phase 8A 저장 거래 메모·카테고리 편집, Phase 8B 월 생활비 목표 로컬 설정, Phase 8C 결정적 Merchant Entity Resolution, Phase 8D 모바일 앱 UI/UX 개편, Phase 8E 대량 분류 검토 큐와 거래 방향 색상 구분, Phase 8F 사용자 확인형 키워드 카테고리 묶기, Phase 9A 확인형 로컬 장부 초기화, Phase 10A 다대다 공동결제 정산은 완료되었다. Phase 10B에서는 거래별 자금통과 자금통별 지출 집계를 진행한다. Git에서 제외한 private 카드 이용내역·계좌 거래내역은 이전 단계의 실제 로컬 브라우저 Preview로 호환성을 확인했다. Phase 8D·8E·8F·9A 반응형 검증에서는 private 파일을 열지 않았다. 저축 분석과 장기 자산 모델은 후속 단계에서 작은 단위로 진행한다.

| FR-044 | MUST | Import Preview는 모든 후보의 기본 자금통 `LIVING`을 표시하고, 사용자는 저장된 거래 편집 화면에서 카테고리와 독립적으로 자금통을 변경할 수 있어야 한다. Preview별 자금통 변경과 Merchant·카테고리 자동 자금통 규칙은 별도 단계에서 결정한다. | 10B |
| FR-045 | MUST | 자금통별 지출은 `EXPENSE + OUTFLOW`만 집계하고 전체 소비 통계는 보존해야 한다. 기존 생활비 카드·월 목표·주간 그래프는 `LIVING` 자금통만 사용한다. 공동결제 정산의 순지출은 사용자가 선택한 하나의 자금통에만 귀속하며, 여러 자금통으로 자동 분할하지 않는다. | 10B |
| FR-047 | SHOULD | 폴더 선택을 지원하는 브라우저에서는 사용자가 직접 고른 로컬 폴더의 최상위 `.xls` 중 가장 최근 파일을 기존 Import Preview 흐름으로 불러올 수 있어야 한다. 폴더 경로·원본 파일명은 저장하거나 표시하지 않고, 미지원 브라우저에서는 기존 파일 선택·끌어놓기를 그대로 제공한다. | 11A |

## Import 요구사항

- 목표 입력 종류는 PDF, CSV, XLSX이지만 각 형식은 실제 필요와 샘플이 확인된 뒤 하나씩 지원한다.
- 첫 파이프라인은 Git에서 제외한 private XLS 구조를 참고한 계좌 거래·카드 이용 legacy XLS Preview로 검증한다. 테스트에는 명백한 가짜 행 배열만 사용한다.
- 금융기관별 Parser/Adapter는 공통 Domain Transaction과 분리한다.
- Adapter의 기본 책임은 해당 파일 처리 가능 여부 확인, 원본 파싱, 공통 모델 정규화다.
- 실제 MyPDS·카드사·은행 형식은 마스킹된 샘플 없이 추측해 구현하지 않는다.

## 데이터 및 계산 요구사항

- KRW 금액은 원 단위 정수로 저장하고 계산한다.
- 통화가 추가되면 해당 통화의 최소 단위 정수와 통화 코드를 함께 사용한다.
- 원본 거래일과 게시일이 모두 필요한 형식에 대비하되, MVP 필드는 실제 사용 사례에 맞춰 최소화한다.
- 날짜·시간은 저장 형식과 표시 시간대를 분리하며 기본 사용자 시간대는 `Asia/Seoul`이다.
- 거래 원본 표현과 정규화된 Merchant 값을 구분할 수 있어야 한다.
- Import 출처와 Batch를 추적해 검토와 문제 분석이 가능해야 한다.

## 급여 추정 요구사항

- Phase 1은 대한민국 일반 직장근로자의 2026년 정책을 사용하는 간편 추정만 지원한다.
- 모든 입력과 결과는 KRW 원 단위 safe integer로 처리하며 표시 문자열을 계산에 재사용하지 않는다.
- 기본 연봉과 월급은 상여를 제외한 세전 기본 급여이고 월 비과세액은 기본 급여에 이미 포함된 금액이다.
- 연간 상여금은 월별 지급액을 계산하지 않고 12개월 월평균에 나눠 한 번만 반영한다.
- 공제대상 가족 수는 본인을 포함해 1명 이상 11명 이하로 제한하고, 8세 이상 20세 이하 자녀 수는 가족 수보다 작아야 한다.
- 근로소득세는 현행 근로소득 간이세액표와 80%·100%·120% 선택 비율을 사용하고 지방소득세를 별도 표시한다.
- 세율, 보험료율, 상·하한, 자녀 공제와 단수 처리 규칙은 기준일을 가진 정책 데이터로 계산 로직과 분리한다.
- 공제 합계와 세전 총액의 차이가 예상 실수령액과 일치해야 하며 모든 결과는 0 이상의 정수여야 한다.

## 비기능 요구사항

### 개인정보와 보안

- MUST: 초기 버전은 원본 금융 파일, 원본 거래 행과 금융 식별자를 외부 서버로 전송하지 않는다. Kakao 설정과 업로드 전 고지가 있는 경우에만 FR-031·FR-034의 미분류 지출 후보 상호명 검색어를 Kakao Local에 전송할 수 있으며, Kakao 검색 이력과 응답은 저장하지 않는다. 원본 설명은 기존 Transaction 계약에 따라 별도로 로컬 저장될 수 있다.
- MUST: 금융기관 ID·비밀번호, 주민등록번호, 공동인증서, 카드 전체 번호를 저장하지 않는다.
- MUST: 실제 금융 샘플은 가능한 범위에서 먼저 마스킹하고 `samples/private/`에만 두며 Git 추적 대상에서 제외한다.
- MUST: 테스트와 예제에는 실제 사람이나 계정을 식별할 수 없는 가짜 데이터만 사용한다.
- MUST: 원본 거래 행, 파일 내용, 민감한 파일명과 금융 식별자를 로그·오류 메시지·테스트 스냅샷에 남기지 않는다.
- MUST: 사용자가 입력한 연봉·월급·상여금과 계산 결과를 console, 오류 메시지, URL, analytics 또는 테스트 fixture에 남기지 않는다.
- MUST: 커밋 전에 추적 대상에 실제 금융 샘플이나 식별 정보가 포함되지 않았는지 확인한다.

### 사용성

- MUST: UI는 360–430px의 작은 화면을 기준으로 먼저 설계하고 넓은 화면에 반응형으로 확장하며, 주요 정보와 조작에 가로 넘침이 없어야 한다.
- MUST: 주요 터치 타깃은 44px 이상이어야 하고, 키보드 사용자는 visible focus와 modal sheet의 Escape·포커스 순환·복귀를 사용할 수 있어야 한다.
- MUST: 재무 요약은 실제 로컬 상태만 반영하며 사용자가 명시적으로 Mock Data 모드를 선택하지 않은 화면에 가상의 금액·건수·진행률을 표시하지 않는다.
- MUST: 앱 셸의 아이콘과 스타일은 로컬 코드로 제공하고 실행 중 외부 디자인 CDN·원격 폰트·원격 아이콘에 의존하지 않는다.
- SHOULD: 운영체제의 reduced-motion 선호를 존중한다.
- MUST: 자동 분류와 중복 판정은 사용자가 저장 전에 확인할 수 있어야 한다.
- SHOULD: 처음 사용하는 흐름에서도 현재 단계와 다음 행동을 알 수 있어야 한다.

## 명시적 제외 사항

다음 항목은 현재 구현하지 않는다.

- 금융기관 계정 또는 인증정보를 이용한 직접 API 연동
- 백엔드와 클라우드 동기화
- AI 기반 카테고리 모델
- OAuth, 알림, Microservice, Event Bus
- Android 네이티브 앱
- 샘플 없는 실제 금융기관 Parser
- 정확한 급여명세서·연말정산·퇴직금 계산과 범용 세무 엔진

## 전체 완료 기준

각 기능은 요구사항별 Acceptance Criteria, 자동 검증, 필요한 수동 사용자 흐름 검증, 관련 문서 갱신을 모두 마치면 `DONE`이다. 사용자만 제공할 수 있는 샘플이나 결정이 필요하면 `NEEDS_USER_INPUT`, 서로 다른 접근을 포함한 3회 시도 후에도 해결하지 못하면 `BLOCKED`로 종료한다.
