# Requirements History

## 2026-08-07 — 대량 분류 검토 큐와 거래 방향 색상 구분

### 추가 요구

분류가 필요한 저장 거래를 장부의 긴 목록에서 하나씩 빠르게 처리하고, 수입과 지출을 행의 상자 색만 봐도 구분할 수 있어야 한다.

### 결정

- `/review`를 canonical 보조 경로로 두고 Home 검토 요약과 Transactions의 검토 필터에서 진입한다. 하단 탐색은 기존 네 항목을 유지한다.
- 큐에는 카테고리가 없는 `EXPENSE`만 넣고, 선택한 카테고리를 해당 Transaction 하나에 저장한 뒤 즉시 다음 거래를 연다. 금액·일자·방향·유형·Import 추적정보와 카테고리 규칙은 바꾸지 않는다.
- `UNKNOWN`은 거래 유형을 검토해야 하는 상태이므로 카테고리 선택만으로 큐에서 해소하지 않는다. 실제 건수와 Transactions로 돌아가는 경로를 별도로 보여 준다.
- 거래 행은 지출에 옅은 로즈, 수입에 옅은 민트를 사용하되 `−`·`+` 부호와 아이콘 대비도 함께 유지한다. 외부 아이콘·이미지 요청은 추가하지 않는다.

### 결과와 제한

큐는 실제 IndexedDB의 현재 미분류 지출만 읽으며 가상의 771건·진행률·금액을 만들지 않는다. 일괄 지정, 자동/AI 추천, 거래 유형 변경과 새 카테고리 규칙 생성은 이 단계에서 제외한다. private XLS를 열지 않고 가짜 테스트 fixture와 빈 로컬 상태로 모바일 화면을 검증했다.

## 2026-08-07 — 모바일 앱 UI/UX 전면 개편

### 확인된 문제

기능별 경로는 이미 분리되어 있었지만 장부 요약과 상세 관리가 한 화면에 섞여 있었고, 상단 중심 탐색과 긴 폼은 360–430px에서 현재 위치와 다음 행동을 빠르게 파악하기 어려웠다. Import 검토, 급여 계산, 목표 설정도 각 기능은 완성되어 있으나 서로 다른 시각 계층과 조작 패턴을 사용했다.

### 결정

- `DESIGN.md`와 제공된 다섯 화면의 시각 방향을 바탕으로 차분한 인디고·민트 토큰, 카드 계층, tabular 금액, 44px 이상 터치 타깃을 공유한다. 외부 폰트·아이콘 CDN이나 원격 이미지는 추가하지 않는다.
- 장부를 실제 로컬 요약 중심 `/home`과 기간 조회·편집 중심 `/transactions`로 나눈다. `/`는 Home, `/ledger`는 Transactions 호환 alias로 유지한다.
- 모바일 하단 탐색은 Home, Transactions, Payroll, Settings만 두고, Import는 Home과 Transactions의 빠른 작업 시트에서 연다. 집중 입력 화면에는 FAB를 표시하지 않는다.
- Home은 실제 저장 거래·정산·설정만 사용한다. 가상 금액은 Transactions에서 사용자가 명시적으로 Mock Data를 고른 경우에만 허용한다.
- 거래 편집과 Import 카테고리 선택은 Escape, 포커스 순환·복귀를 지원하는 모바일 sheet로 통일한다. Import의 읽기·Kakao 분석·저장은 실제 비동기 상태와 실제 후보 수만 보여준다.
- 급여 계산과 목표 설정의 도메인·저장 경계는 바꾸지 않고 입력, 결과, 경고, 근거의 시각 순서만 재구성한다.

### 결과와 제한

Home, Transactions, Import, Payroll, Settings는 360–430px 모바일을 기준으로 재구성하고 768·1280px까지 가운데 정렬 확장한다. 새 Insights·Assets·프로필·수동 거래·공유 기능은 만들지 않았고, private XLS 없이 빈 로컬 상태와 가짜 메모리 입력만으로 반응형·키보드 흐름을 검증했다. 최종 리뷰에서 확인 필요 거래의 의미를 Import와 통일하고, 느린 저장 결과가 새 Preview 상태를 덮지 못하도록 요청 세대 가드를 추가했다.

## 2026-08-07 — Vector Search보다 Merchant Entity Resolution 우선

### 확인된 문제

Kakao `category_name` 기반 카테고리 제안을 도입했지만 카드사 Merchant Name과 Kakao Place Name이 같은 브랜드를 서로 다르게 표기하면 검색과 동일 상호 판정이 실패했다. 대표적으로 `지에쓰이십오 대전법동점`과 `GS25 대전법동점`, `씨유`와 `CU`는 의미 유사도가 아니라 동일 Entity의 표기 차이다.

### 결정

- 기존 정확 `CategoryRule`을 최우선으로 유지하고, 일치하면 Fuzzy와 Kakao를 호출하지 않는다.
- 원문을 보존하는 Unicode NFKC·기호·공백 정규화, 중앙 Alias Registry, 지점명을 보존하는 canonical query를 도입한다.
- GS25, CU, 7-ELEVEN, 메가MGC커피의 확인된 표기만 Alias로 관리한다. 범용 한글 숫자 변환이나 공격적인 법인·suffix 삭제는 하지 않는다.
- Exact·Alias 실패 뒤에만 Registry 후보를 대상으로 편집 거리 1 이하의 제한적 Fuzzy를 적용한다. 단일 안전 후보가 아니면 Review로 둔다.
- Kakao는 원문, 정규화 표시값, canonical query를 중복 제거해 최대 3회 검색한다. `category_name`이 매핑되고 원문 정확 일치 또는 안전한 canonical 동일성이 확인될 때만 카테고리를 제안한다.
- `PAYCO오더` 등 결제 중개자와 그 구두점·전각 변형은 Alias·Fuzzy·Kakao에 전달하지 않는다.
- Original부터 최종 Review 이유까지의 분석 과정은 Preview에서 필요할 때만 펼쳐 보고 저장·로그하지 않는다.

### 측정과 제한

명백한 가짜 Merchant 14건의 classifier fixture에서 해석 출처는 `EXACT 4 / ALIAS 7 / FUZZY 1 / USER_RULE 1 / REVIEW 1`이었다. 미리 제공한 가짜 Kakao 장소 결과를 기준으로 한 분류 결과는 기존 `KAKAO 4 / USER_RULE 1 / REVIEW 9`에서 `KAKAO 12 / USER_RULE 1 / REVIEW 1`로 바뀌었다.

이 수치는 실제 Kakao 검색 성공률이나 운영 데이터 정확도가 아니다. 각 Merchant에 기대 장소 결과가 이미 주어졌을 때 classifier가 표기 차이를 처리하는지 비교한 재현 가능한 테스트 수치다.

### 보류

사용자 수정 한 건에서 넓은 브랜드 Alias를 자동 학습하지 않는다. 사용자 관리 Alias, 성공 Merchant Cache, 법인 wrapper·영업 suffix 처리에는 저장·수정·삭제 정책과 별도 fixture가 필요하다. Normalize + Alias + Fuzzy + Kakao 이후에도 의미 기반 추천 문제가 충분히 많이 남는다는 측정 전에는 Vector DB나 Embedding을 도입하지 않는다. 자세한 결정은 [ADR-0012](../adr/ADR-0012-merchant-entity-resolution-before-vector-search.md)를 따른다.

## 2026-08-05 저장 거래별 메모·카테고리 직접 수정 추가

### 추가 요구

저장된 거래마다 메모를 남기고 카테고리를 나중에 바로잡을 수 있어야 하며, 장부 목록에서 카테고리를 빠르게 구분할 수 있는 대표 아이콘이 필요하다.

### 결정

- 장부의 저장 거래마다 하나의 인라인 편집기를 열어 카테고리와 선택 메모를 수정하거나 비울 수 있게 한다.
- 수정은 선택한 Transaction에만 적용하고, 금액·일자·유형·Import 출처는 보존한다. 확인된 카테고리 규칙을 새로 만들거나 변경하지 않는다.
- 빈 메모와 미분류 카테고리는 Transaction 필드에서 제거하고, 저장 전 전체 Transaction을 다시 검증한다.
- 외부 아이콘·이미지 요청 없이 고정된 Unicode 이모지를 카테고리 표시로 사용한다.

### 변경 이유

Import 시점의 자동 제안은 나중의 실제 상황을 모두 알 수 없다. 거래별 후속 메모와 카테고리 수정은 원장을 보존하면서 가계부 분석 정확도를 높인다.

## 2026-08-05 Kakao 장소 주소 표시에서 카테고리 제안으로 보정

### 확인된 문제

Kakao 키워드 장소 검색은 수행했지만 결과의 주소만 Preview에 표시했다. `category_name`은 내부 카테고리로 연결되지 않았고, 카테고리 그룹·좌표도 버려져 장소 분류 목적과 구현이 어긋났다.

### 결정

- `category_name`을 제한된 내부 지출 카테고리 제안으로 매핑한다.
- 사용자 규칙을 최우선으로 두고, 향후 캐시·정적 규칙을 추가해도 `사용자 규칙 > 캐시 > 정적 규칙 > Kakao > 검토` 순서를 지킨다.
- 정규화한 거래처명과 장소명이 정확히 일치할 때만 HIGH로 제안한다. 결제 중개자, 불일치, 미매핑은 자동 분류하지 않는다.
- Preview에서 거래처명, Kakao 카테고리·그룹, 주소, 제안 카테고리, 출처, 신뢰도를 확인하고 Kakao 메타데이터는 저장하지 않는다.

### 변경 이유

주소는 장소 확인의 보조 정보일 뿐이고, 가계부의 필요한 결과는 거래처 카테고리다. 엄격한 매칭과 검토 경로를 두면 자동 제안의 편의성과 잘못된 생활비 분류 방지를 함께 유지할 수 있다.

현재 요구사항 자체는 [requirements.md](requirements.md)를 기준으로 하며, 이 문서는 변경 전후와 결정 이유를 시간순으로 보존한다.

## 2026-08-05 — 금융 API 자동 연동에서 파일 Import로 전환

### 최초 요구

금융기관 API로 사용자의 계좌·카드 소비내역을 자동 조회해 가계부를 만든다.

### 확인된 문제

대한민국에서 개인 개발자가 자신의 금융 데이터를 공식 API로 자유롭게 연동하기 어렵다는 제약을 프로젝트 전제로 확인했다.

### 변경

사용자가 MyData/MyPDS 또는 금융기관에서 직접 내려받은 PDF, CSV, XLSX를 가져와 파싱·분류하는 흐름으로 바꾼다.

### 변경 이유

사용자가 데이터에 대한 통제권을 유지하면서 현실적으로 구현 가능한 경로이기 때문이다.

### 현재 결정

파일 Import를 우선 개발하며, 실제 금융 형식은 마스킹된 샘플이 확보된 뒤 Adapter 단위로 지원한다. 자세한 내용은 [ADR-0001](../adr/ADR-0001-file-import-over-financial-api.md)을 따른다.

### 현재 결정

## 2026-08-05 — Phase 1 급여 실수령 추정기 추가

### 추가 요구

다음 작업에 앞서 세전 연봉 또는 월급과 상여금을 입력해 예상 실수령액을 확인할 수 있는 간단한 계산기를 만든다.

### 확인된 제약

- 근로소득 원천징수는 고정 세율이 아니라 과세 월급여, 공제대상 가족 수와 자녀 수에 따른 간이세액표를 사용한다.
- 상여의 실제 원천징수액은 지급대상기간, 이전 급여와 이미 납부한 세액에 따라 달라져 연간 상여 총액만으로 지급월 실수령액을 확정할 수 없다.
- 계산 결과를 실제 `INCOME` 거래로 만들면 이후 Import 기반 장부와 예상값이 섞인다.

### 변경

Phase 1을 Web Skeleton `1A`와 급여 실수령 추정기 `1B`로 나눈다. 사용자는 연봉·월급 입력 모드, 별도 연간 상여금, 월 비과세액, 공제대상 가족·자녀 수와 원천징수 비율을 입력한다. 상여금은 12개월 월평균으로 반영한다.

### 현재 결정

- 공식 근거와 기준일을 가진 2026년 계산 정책을 브라우저에서 로컬로 실행한다.
- 결과는 연간·월평균 예상액이며 공식 급여명세서나 세무 결과로 표현하지 않는다.
- Phase 1 입력과 결과는 메모리에만 두고 저장·URL 반영·거래 생성을 하지 않는다.
- Phase 6에서 실제 Import된 `INCOME`과 예상값을 비교할 수 있지만 자동 합산하거나 대체하지 않는다.
- 개인별 기본값 저장, 연말정산, 상여 지급월별 법정 원천징수와 여러 연도 비교는 별도 후속 요구가 확인된 뒤 계획한다.

자세한 계산 경계와 정책 갱신 방식은 [ADR-0004](../adr/ADR-0004-versioned-local-payroll-estimation.md)를 따른다.

## 2026-08-05 — Generic CSV에서 private 샘플 기반 Legacy XLS Preview로 변경

### 최초 요구

Phase 3은 명시적인 가짜 CSV 형식부터 시작한다.

### 확인된 정보

사용자가 Git에서 제외된 `samples/private/`에 계좌 거래내역과 카드 이용내역 legacy XLS를 제공했다. 두 파일은 날짜·금액·거래 상태 표현이 다른 별도 레이아웃이며, 실제 처리 가능 범위를 확인할 수 있다.

### 변경

Phase 3A는 두 private XLS 구조를 참고한 브라우저 전용 Preview로 시작한다. 계좌 행은 경제적 유형을 `UNKNOWN`으로 유지하고, 카드 취소·외화 후보는 자동 반영하지 않는다. 확정 저장은 별도 Phase 3B vertical slice다.

### 변경 이유

실제 사용 파일 구조를 바탕으로 Import를 검증하되, 원본 파일과 개인 금융 데이터를 Git·테스트·오류·로그에 남기지 않기 위해서다.

### 현재 결정

- `.xls` 파일은 사용자가 선택한 브라우저 File API 바이트로만 읽는다.
- private 샘플의 값·파일명·기관 식별자는 코드와 문서에 기록하지 않는다.
- 테스트는 같은 구조를 가진 명백한 가짜 행 배열만 사용한다.
- Native IndexedDB 저장은 Preview 검증 이후의 다음 vertical slice에서 구현한다.

자세한 계약은 [Legacy XLS Import Contract](../architecture/import-xls-contract.md)를 따른다.

## 2026-08-05 — 로컬 저장 기간 조회와 단체 결제 순지출 집계 추가

### 추가 요구

사용자는 브라우저 로컬에 저장된 거래를 하루, 1주, 1달, 직접 선택한 기간으로 보고 싶다. 또한 단체 결제를 먼저 하고 다른 사람에게 정산금을 받은 경우, 생활비 목표에는 결제 금액과 정산 입금을 합친 실제 부담액만 반영되기를 원한다.

### 결정

- 기간은 `occurredOn` 기준의 양끝 포함 범위이며, 1주는 선택일과 앞선 6일, 1달은 선택일이 속한 달로 정한다.
- 단체 결제는 자동 추론하지 않고, 사용자가 원결제 출금 1건과 정산 입금 1건 이상을 직접 연결한다.
- 생활비에는 `max(원결제 출금 - 연결한 정산 입금 합계, 0)`만 계산하고, 원장·잔액·원본 거래는 변경하지 않는다.
- 정산 입금일이 원결제일보다 늦더라도 생활비 부담은 원결제일에 귀속한다.

### 변경 이유

입금 자체를 삭제하거나 지출 거래를 수정하면 실제 현금흐름을 잃는다. 별도 연결과 순지출 집계라야 원장을 보존하면서 생활비 목표의 의미를 유지할 수 있다. 자세한 기술·도메인 결정은 [ADR-0005](../adr/ADR-0005-manual-shared-payment-settlements.md)를 따른다.

## 2026-08-05 — 중복 가능 후보 검토와 명시적 재포함 추가

### 최초 요구

저장된 거래와 새 Import Preview에 같은 거래가 있을 수 있음을 확인하되, 실제 거래일 수도 있으므로 기존 거래를 자동으로 삭제하거나 합치지 않는다.

### 확인한 문제

같은 날짜·금액·설명을 사용하는 별도 결제가 가능하고, 카드 및 계좌 추출 형식에 따라 설명과 결제수단이 달라질 수 있다. 단순한 자동 중복 제거는 원장과 생활비 분석을 잘못 바꿀 위험이 있다.

### 결정

동일한 v1 비교 지문을 가진 저장 거래 또는 Preview 내 앞선 후보를 중복 가능성으로 표시하고, 해당 후보는 기본 저장에서 제외한다. 사용자가 후보별 또는 전체 재포함을 명시한 경우에만 저장하며, 기존 거래는 변경하지 않는다.

### 변경 이유

반복 Import로 인한 이중 집계 위험을 줄이면서도 정상적인 반복 결제를 보존하려면, 알고리즘은 검토 신호를 제공하고 최종 결정은 사용자에게 남겨야 한다. 자세한 기술·도메인 결정은 [ADR-0006](../adr/ADR-0006-duplicate-candidates-require-user-confirmation.md)를 따른다.

## 2026-08-05 — 확인한 거래 설명 카테고리 규칙 추가

### 최초 요구

처음 보는 거래 설명은 사용자가 카테고리를 정하고, 같은 설명에는 사용자가 동의한 규칙만 다시 적용한다. 자동 분류 결과는 저장 전에 바꿀 수 있어야 한다.

### 확인한 문제

현재 XLS에는 신뢰할 수 있는 별도 상호 필드가 없고, 거래 설명이 같아도 소비 맥락은 다를 수 있다. 규칙을 자동으로 만들거나 과거 거래를 소급 변경하면 잘못된 생활비 분석을 고정할 수 있다.

### 결정

정규화한 거래 설명의 정확 일치만으로 규칙을 조회하고, Preview에서 보이는 카테고리를 사용자가 다시 선택할 수 있게 한다. 카테고리가 지정된 저장 후보에 대해 별도의 규칙 저장 동의를 한 경우에만 규칙을 생성 또는 교체한다.

### 변경 이유

설명 가능하고 되돌릴 수 있는 사용자 주도 분류를 먼저 검증해야 향후 상호 기반 매칭, 사용자 정의 카테고리, 퍼지 매칭을 안전하게 확장할 수 있다. 자세한 기술·도메인 결정은 [ADR-0007](../adr/ADR-0007-confirmed-description-category-rules.md)를 따른다.

## 2026-08-05 — 기능별 페이지 분리와 카테고리 빠른 선택 추가

### 추가 요구

하나의 긴 화면 대신 급여 계산, 장부, XLS 가져오기를 각각 보기 쉬운 페이지로 나눈다. Import Preview의 카테고리 선택도 긴 select 목록보다 빠르고 명확한 방식으로 다듬는다.

### 결정

- `/ledger`, `/imports`, `/payroll`을 각 기능의 브라우저 경로로 사용하고, 앱 내부 탐색은 History API와 `popstate`로 뒤로/앞으로를 반영한다.
- Import 후보는 현재 카테고리를 버튼으로 표시하고, 필요할 때만 카테고리 빠른 선택판을 연다. 선택과 “이 설명 기억” 규칙 동의는 독립된 조작으로 유지한다.
- 이 Slice는 화면 구조와 분류 검토 경험만 다룬다. 사용자 생활비 목표·저축 분석·사용자 정의 카테고리는 후속 Phase 6 Slice에서 결정한다.

### 변경 이유

주간 Import, 장부 확인, 급여 추정은 서로 다른 목적과 집중 상태를 요구한다. 기능별로 분리하면 긴 스크롤과 상태 혼합을 줄이고, 파일 검토 중 카테고리 판단에 집중할 수 있다.

### 현재 결정

클라이언트 경로 정책과 배포 전제는 [ADR-0008](../adr/ADR-0008-client-routes-for-financial-workflows.md)에, 카테고리 규칙의 보존 원칙은 [ADR-0007](../adr/ADR-0007-confirmed-description-category-rules.md)에 기록한다.

## 2026-08-05 카드 소비 기준과 계좌 현금흐름 유형 분류 추가

### 확인한 변화

실제 카드 이용내역과 계좌 거래내역은 같은 소비를 서로 다른 시점과 표현으로 담는다. 카드 구매와 계좌 카드대금 출금을 모두 소비로 처리하면 생활비가 중복된다. 또한 계좌에는 저축, 대출상환, 이체, 수입, 리워드가 섞여 있어 카테고리만으로 성격을 표현할 수 없다.

### 결정

- 카드 이용내역을 `EXPENSE + OUTFLOW` 소비의 우선 출처로 둔다.
- 계좌 Import 후보는 카테고리보다 먼저 작고 설명 가능한 규칙으로 거래 유형을 분류한다. Preview에는 유형, 비식별 근거 코드, 확신 수준을 표시한다.
- 계좌 `CARD_PAYMENT`는 현금흐름으로 저장하며 생활비에서 제외한다. 카테고리는 새 `EXPENSE` Preview 후보에만 적용한다.
- 본인 계좌 별칭이 없는 상태에서 `SELF_TRANSFER`를 추정하지 않는다. 모호한 이체는 검토 가능한 `TRANSFER` 또는 `UNKNOWN`으로 둔다.

### 후속으로 미룬 사항

사용자 계좌 별칭 설정, 이체 상대 검증, 상호·브랜드 정규화, 확장 카테고리, 사용자 규칙 관리, 외부 제공자 API는 별도 단계에서 설계한다. 원본 파일, 계좌·카드 번호, 개인 이름, 실제 거래 문구·금액은 문서와 테스트에 기록하지 않는다. 상세 결정은 [ADR-0009](../adr/ADR-0009-card-expense-and-account-cashflow-classification.md)를 따른다.

## 2026-08-05 Kakao Map Web SDK 설정 경계 추가

### 결정

Kakao 장소 검색은 브라우저에 노출되는 JavaScript 키와 등록된 JavaScript SDK 도메인을 사용하는 Web SDK로만 준비한다. `.env.example`에는 `VITE_KAKAO_MAP_JAVASCRIPT_KEY`의 빈 값만 제공하고 REST API key, Admin key, client secret, access token은 포함하지 않는다.

실제 거래 설명을 외부로 보내는 검색은 자동 실행하지 않는다. 이후 한 후보씩 사용자가 명시적으로 요청하고 전송 사실을 확인하는 Preview 전용 흐름으로만 추가한다. 결과는 자동 저장·자동 카테고리화·백그라운드 동기화에 사용하지 않는다.

### 이유

상호 확인 보조 기능의 편의성과 local-first 금융 데이터 경계를 함께 지키기 위해서다. 키 없는 개발·검증 환경도 기존 기능이 모두 동작해야 한다. 상세 결정은 [ADR-0010](../adr/ADR-0010-kakao-map-web-sdk-opt-in-boundary.md)을 따른다.

## 2026-08-05 — 월 생활비 목표의 로컬 설정과 잔액 추가

### 추가 요구

사용자는 실제로 저장된 거래를 바탕으로 생활비 목표와 남은 금액을 확인하고, 목표 금액을 코드 수정 없이 이 기기에서 직접 바꾸고 싶다.

### 결정

- `/settings`에서 월 생활비 목표 하나를 양의 KRW 정수로 저장·변경·비울 수 있게 한다.
- 목표는 IndexedDB의 단일 로컬 설정 레코드에만 저장한다. 실제 목표 금액을 코드, 문서, 테스트 fixture, URL, 외부 API에 넣지 않는다.
- 월간 장부에서만 `목표 - 순생활비`를 남은 금액 또는 초과 금액으로 보인다. 공동결제는 기존 수동 정산 연결에 따른 순지출을 그대로 사용한다.
- 하루, 1주, 직접 선택 기간에는 월 목표를 임의로 일할 계산하지 않고 실제 사용액만 보인다.
- 급여 계산기의 입력·결과는 계속 메모리 전용으로 유지하며 Settings와 연결하지 않는다.

### 변경 이유

생활비 목표는 개인별 정책이므로 예시 기본값이나 임의의 기간 비례 정책을 강요하면 잘못된 판단을 만들 수 있다. 월 목표의 의미를 먼저 작고 설명 가능한 흐름으로 제공하고, 주간 목표·저축 가능액·장기 자산은 별도 요구로 확장한다. 자세한 경계는 [ADR-0011](../adr/ADR-0011-local-monthly-living-expense-goal.md)을 따른다.
