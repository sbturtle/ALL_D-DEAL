# Product Context

## 제품 한 문장

주말에 금융기관에서 내려받은 거래 파일을 사용자가 확인 가능한 절차로 정리하고, 생활비와 장기 자산 목표를 함께 추적하는 개인용 local-first 가계부다.

## 시작 배경

사용자는 소비가 발생할 때마다 가계부를 직접 입력하고 싶지 않다. 처음에는 국내 금융기관 API로 계좌와 카드 내역을 자동 조회하려 했으나, 개인 개발자가 자신의 금융 데이터를 공식 API로 자유롭게 연동하기 어렵다는 제약을 프로젝트 전제로 확인했다.

실시간성이 꼭 필요하지도 않다. 사용자가 원하는 리듬은 주말마다 약 한 번 금융기관 또는 MyData/MyPDS에서 자신의 데이터를 내려받고, 애플리케이션이 이를 자동 정리하도록 하는 것이다. 따라서 제품의 출발점은 계정 연동이 아니라 사용자가 소유한 파일을 안전하게 가져오는 흐름이다.

이 변화의 상세 근거는 [ADR-0001](../adr/ADR-0001-file-import-over-financial-api.md)과 [ADR-0003](../adr/ADR-0003-weekly-import-instead-of-realtime.md)에 기록한다.

## 해결하려는 문제

- 반복적인 수기 입력 부담 때문에 지출 기록이 누락된다.
- 카드 사용, 카드 결제대금, 계좌 이체를 모두 소비로 보면 금액이 이중 집계된다.
- 서로 다른 금융기관의 내역은 형식과 표현이 달라 한눈에 비교하기 어렵다.
- 생활비뿐 아니라 저축, 주거·결혼자금, 청약, 투자, 학자금대출을 하나의 재무 흐름으로 보고 싶다.
- 금융 데이터가 외부 서비스로 전송되는 데 대한 부담이 있다.

## 핵심 사용자 흐름

```text
금융기관/MyData에서 파일 다운로드
→ 가계부에 파일 선택
→ 형식 분석 및 공통 거래 모델로 정규화
→ 신규·중복·확인 필요 항목 Preview
→ 사용자 확인 및 수정
→ 확정된 거래만 로컬 저장
→ 주간·월간 집계와 목표 확인
```

파일을 선택한 즉시 저장하지 않고 `Preview → Confirm → Commit` 단계를 지키는 것이 핵심이다.

## 사용자 재무관리 맥락

현재 계획 수립의 배경에는 다음 맥락이 있다.

- 월 생활비 상한을 정하고 소득에서 생활비를 제외한 금액을 가능한 한 저축하려 한다.
- 현재 금융자산 형성 초기이며 취업후상환 학자금대출을 관리해야 한다.
- 주택청약 자산을 유지하면서 향후 독립과 결혼에 필요한 자금을 준비하려 한다.
- 주거·결혼자금, 비상금, 청약, 투자, 대출을 분리해 장기 순자산 변화를 보고 싶다.

정확한 소득·생활비·부채 금액, 거주 지역, 목표 시점은 민감한 사용자 데이터이므로 Git 추적 문서나 코드 상수로 저장하지 않는다. 해당 값은 Settings 기능이 생기면 사용자가 로컬에 입력하고 수정할 수 있는 데이터로 다룬다.

## 제품 목표

### 단기

- 가짜 데이터로 모바일 우선 Dashboard와 거래 흐름을 검증한다.
- 공통 Transaction 모델과 브라우저 로컬 저장 기반을 만든다.
- Generic Test Format CSV로 Import 전체 흐름을 검증한다.

### 중기

- 중복 탐지와 거래 유형 분류로 이중 집계를 줄인다.
- 사용자가 확인한 Merchant→Category 규칙을 재사용한다.
- 주간·월간 생활비와 저축 가능액을 보여준다.
- 마스킹된 실제 샘플을 근거로 첫 금융기관 Adapter를 구현한다.

### 장기

- 주거·결혼자금, 비상금, 청약, 투자, 대출과 순자산 변화를 추적한다.
- 웹 MVP가 검증된 뒤 Galaxy 환경에 적합한 PWA 또는 Android 전략을 결정한다.

## 제품 원칙

1. 금융 데이터는 기본적으로 사용자 기기 밖으로 보내지 않는다.
2. 자동화 결과를 사용자가 저장 전에 검토하고 수정할 수 있어야 한다.
3. 모든 출금을 소비로 취급하지 않고 거래의 경제적 의미를 구분한다.
4. 실제 금융 파일 형식은 샘플 없이 추측하지 않는다.
5. AI 분류보다 설명 가능하고 수정 가능한 규칙 기반 분류로 시작한다.
6. Mobile First로 설계하되 검증되지 않은 Android 구현을 앞당기지 않는다.
7. 한 번에 작은 Vertical Slice 하나만 구현하고 검증 근거를 남긴다.

## 성공의 초기 기준

- 사용자가 일주일치 거래를 한 번의 Import 흐름으로 검토할 수 있다.
- 같은 입력을 반복해도 중복 가능성이 명시되고 무조건 저장되지 않는다.
- 카드 사용액과 카드 결제대금이 소비로 이중 집계되지 않는다.
- 생활비 목표와 잔액을 모바일 화면에서 빠르게 파악할 수 있다.
- 실제 금융 데이터가 외부 서버나 Git 저장소로 유출되지 않는다.
