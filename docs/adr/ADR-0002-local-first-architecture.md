# ADR-0002 초기 버전에 local-first 아키텍처 채택

- 날짜: 2026-08-05
- 관련 결정: [ADR-0001 파일 Import](ADR-0001-file-import-over-financial-api.md), [ADR-0003 주 1회 Import](ADR-0003-weekly-import-instead-of-realtime.md)

## 상태

Accepted

## 최초 사용자 요구

웹 애플리케이션을 로컬에서 충분히 검증하고, 장기적으로 Galaxy Android 환경까지 확장하고자 한다.

## 이후 대화에서 확인된 문제

입력 데이터에는 매우 민감한 금융 거래가 포함된다. 현재는 계정 공유, 다중 기기 동기화, 원격 분석 요구가 없으므로 백엔드를 먼저 만들 실익이 없다.

## 변경된 요구사항

금융 파일 파싱, 거래 검토, 저장, Dashboard 집계를 가능한 한 사용자 브라우저 안에서 수행한다. 외부 서버는 현재 범위에서 제외한다.

## 결정

초기 데이터 흐름을 `Browser → Parser → IndexedDB → Dashboard`로 설계한다. UI와 Parser는 Application/Domain 경계를 통해 분리하고, 브라우저 저장 구현이 Domain 규칙의 의존 대상이 되지 않도록 한다.

## 결정 이유

- 금융 데이터가 사용자 PC 밖으로 나가는 기본 경로를 제거한다.
- 서버 운영, 사용자 인증, 전송 보안, 동기화 충돌을 현재 핵심 문제에서 분리한다.
- Web Skeleton과 Import 흐름을 더 작은 범위에서 검증할 수 있다.

## 고려한 대안

### 초기부터 백엔드 저장

멀티디바이스에는 유리하지만 현재 필요하지 않은 보안·운영 복잡도를 만든다.

### 파일만 사용하고 브라우저 저장 안 함

데이터 노출은 적지만 누적 집계, 규칙 재사용, 주간 비교를 제공하기 어렵다.

## 장점

- 데이터 노출 면적과 초기 운영 비용이 작다.
- 핵심 데이터 처리에 외부 데이터 서버 연결이 필요하지 않다.
- 삭제와 초기화를 사용자가 통제하기 쉽다.

## 단점

- 브라우저 데이터 삭제 시 손실될 수 있어 향후 백업·복구 전략이 필요하다.
- 기기 간 자동 동기화를 제공하지 않는다.
- 브라우저 저장 용량과 파일 처리 성능 제약을 받는다.
- local-first는 저장 데이터가 자동으로 암호화된다는 뜻이 아니다. 감염된 PC나 악성 브라우저 확장까지 방어한다고 주장하지 않는다.

## 향후 다시 검토할 조건

- Galaxy와 PC 사이의 동기화가 핵심 요구가 된다.
- 브라우저 저장 한계가 실제 데이터 규모에서 확인된다.
- 공유 가계부나 다중 사용자 기능이 필요해진다.
- 이때 백엔드뿐 아니라 암호화, 내보내기/가져오기, PWA 유지 방안도 함께 비교한다.
