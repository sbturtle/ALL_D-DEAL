# ADR-0015 — 지출 카테고리와 자금통을 분리하고 단일 자금통을 우선한다

- 상태: 채택
- 최초 결정일: 2026-08-10
- 관련 요구사항: FR-010, FR-011, FR-040, FR-041, FR-042, FR-043, FR-044, FR-045
- 관련 결정: [ADR-0007](ADR-0007-confirmed-description-category-rules.md), [ADR-0009](ADR-0009-card-expense-and-account-cashflow-classification.md), [ADR-0011](ADR-0011-local-monthly-living-expense-goal.md), [ADR-0013](ADR-0013-confirmed-local-ledger-reset.md), [ADR-0014](ADR-0014-many-to-many-shared-payment-settlements.md)

## 최초 사용자 요구

모든 소비가 사실상 생활비 하나에 집계되는 구조를 고치고, 같은 카테고리의 소비라도 생활비·비정기비·비상금·주거·결혼·저축·투자처럼 돈의 목적을 구분해 관리한다. 장래에는 수입을 여러 목적에 배분하고 사용자가 자금통을 직접 만들 수 있어야 한다.

## 이후 대화에서 확인된 문제

기존 `Expense Category`는 무엇에 사용했는지를 나타내는 분류이며, 어떤 목적의 돈을 썼는지를 표현하지 못한다. 카테고리와 자금 목적을 하나의 enum이나 규칙에 합치면 가령 의료비가 일상 생활비인지 비상금 사용인지 사용자가 수정할 수 없고, Merchant·Kakao 카테고리 제안이 자금 계획까지 임의로 바꾸게 된다.

10A단계의 공동결제 정산은 여러 지출·수입을 한 묶음으로 연결한다. 연결 지출이 서로 다른 자금통에 속할 수 있으므로 정산 입금을 자금통별로 자동 분할하면 근거 없는 배분·반올림·이중 차감 위험이 생긴다.

## 변경된 요구사항

거래와 공동결제 정산에 자금통을 명시적으로 저장하고, 기존 생활비 카드·월 목표·주간 그래프는 전체 소비가 아니라 생활비 자금통만 사용한다. 기존 데이터는 손실 없이 읽혀야 하며, 로컬 초기화 뒤에는 기본 자금통이 다시 준비되어야 한다.

## 결정

- 코드에서는 `BudgetBucket`, 사용자 화면에서는 **자금통**이라는 이름을 사용한다. Category는 무엇에 사용했는지, 자금통은 어느 목적의 돈으로 관리하는지를 뜻하며 서로 대체하지 않는다.
- `BudgetBucket`은 `id`, `name`, `icon`, `order`, `isDefault`, `isArchived`를 가진 로컬 레코드다. 초기 IndexedDB에는 `LIVING`, `IRREGULAR`, `EMERGENCY`, `SAVING`, `HOUSING_MARRIAGE`, `INVESTMENT`, `OTHER`의 7개 레코드를 seed한다.
- `BudgetBucketId`는 고정 enum이 아닌 공백 없는 문자열이다. 현재 기본 목록 이외의 ID도 Transaction·정산 검증에서 허용해 이후 사용자 정의 자금통을 저장할 수 있게 한다. 이번 단계에서는 생성·수정·보관 관리 화면을 만들지 않는다.
- 모든 Transaction과 `BudgetSettlement`은 하나의 필수 `budgetBucketId`를 가진다. 한 Transaction 금액을 여러 자금통으로 나누는 `TransactionAllocation[]`은 만들지 않는다.
- IndexedDB v6 업그레이드는 자금통이 없는 모든 기존 Transaction과 정산에 `LIVING`을 넣고 기본 자금통 7개를 저장한다. 이 값은 legacy 기본값이며 과거 거래의 실제 목적을 판정한 결과가 아니다.
- Legacy XLS Import Preview의 모든 후보는 `LIVING` 기본값을 표시한다. 사용자는 확정 뒤 거래 편집 시트에서 자금통을 독립적으로 바꾼다. Preview별 자금통 변경과 Merchant·카테고리 기반 자동 자금통 규칙은 이번 범위에 넣지 않는다.
- 자금통별 지출은 `EXPENSE + OUTFLOW`만 집계한다. 전체 소비 통계는 모든 자금통 지출을 유지하고, 기존 생활비 카드·월 목표·주간 그래프는 `LIVING` 자금통 요약만 사용한다.
- 공동결제 정산의 순지출은 사용자가 정한 정산의 `budgetBucketId` 하나에만 귀속한다. 여러 자금통으로 정산금을 자동 분할하지 않는다.
- 로컬 장부 초기화는 사용자 정의 자금통을 포함한 `budgetBuckets`를 비운 뒤, 같은 IndexedDB 트랜잭션에서 기본 자금통 7개를 다시 저장한다.

## 결정 이유

단일 자금통은 현재 사용자가 거래 목적을 빠르게 바로잡을 수 있게 하면서도, 분할 배분의 금액 규칙과 반올림 정책을 섣불리 만들지 않는다. 별도 저장소와 열린 문자열 ID는 고정 카테고리에 갇히지 않고 사용자 정의 자금통을 추가할 경로를 남긴다. 정산에 명시적 자금통을 두면 다대다 관계에서도 하나의 순지출이 어느 목적에 속하는지 사용자가 설명할 수 있다.

## 고려한 대안

1. 카테고리에 자금 목적을 합치기: 같은 카테고리의 예외 거래를 표현할 수 없고, 카테고리 확장과 자금 계획이 함께 흔들리므로 선택하지 않았다.
2. `Expense` 거래에만 자금통을 두기: 수입·저축·이체를 포함한 향후 배분 구조가 막히므로 선택하지 않았다.
3. 처음부터 `TransactionAllocation[]`을 구현하기: 금액 분할, 합계 검증, 수정·삭제, 공동결제와의 관계를 모두 정해야 하므로 현재 요구보다 넓어 선택하지 않았다.
4. 카테고리 또는 Merchant에서 자금통을 자동 확정하기: 일상 의료비와 비상 의료비처럼 맥락 예외가 많고, 사용자의 자금 계획을 잘못 바꿀 위험이 있어 선택하지 않았다.
5. 다대다 정산 입금을 지출 자금통 비율로 자동 분할하기: 사용자가 의도한 분담과 다를 수 있고 반올림 규칙도 필요하므로 선택하지 않았다.

## 장점

- 전체 소비와 생활비·비정기비·비상금 등 목적별 지출을 구분한다.
- 원본 거래·일반 입출금 합계·잔액과 카테고리 규칙을 보존한다.
- 기존 로컬 데이터와 정산을 손실 없이 v6 모델로 읽는다.
- 사용자 정의 자금통, 자금통별 목표, 수입 배분을 추가할 저장 경계를 마련한다.

## 단점

- 기존 데이터의 `LIVING` 값은 실제 목적이 아니라 legacy 기본값이므로 사용자가 필요하면 거래별로 수정해야 한다.
- Import Preview에서는 자금통을 확인만 할 수 있고 변경할 수 없다.
- 공동결제 순지출과 한 거래 금액을 여러 자금통에 나누지 않는다.
- 자금통 생성·이름 변경·보관과 예산 목표 관리는 아직 제공하지 않는다.

## 향후 다시 검토할 조건

사용자가 급여·상여 등 수입을 여러 자금통에 배분하거나, 하나의 지출·공동결제 정산을 여러 목적에 나누거나, 자금통별 월 목표·저축 목표·보관 관리를 요구하면 `TransactionAllocation[]` 또는 별도 배분 엔터티, 합계·반올림·수정 정책, 정산과의 연결 규칙을 포함한 후속 ADR로 재검토한다.
