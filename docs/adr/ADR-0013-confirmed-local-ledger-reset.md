# ADR-0013 — 확인형 로컬 장부 초기화

- 상태: 채택
- 최초 결정일: 2026-08-07
- 수정일: 2026-08-10

## 최초 사용자 요구

사용자가 로컬 장부를 초기화할 수 있는 버튼을 원하며, 초기화 전에 재확인 모달을 보여 달라고 요청했다.

## 이후 대화에서 확인된 문제

로컬 우선 장부는 브라우저 저장소에 거래, Import 이력, 정산, 분류 규칙, 목표와 사용자 자금통을 함께 유지한다. 단순한 삭제 버튼은 삭제 범위가 불명확하고 실수로 누른 경우 되돌릴 수 없는 금융 기록 손실을 만들 수 있다. 반대로 IndexedDB 데이터베이스 자체를 삭제하면 스키마 재생성·다른 열린 탭·테스트가 얽혀 실패 경계가 넓어진다.

## 변경된 요구사항

초기화는 이 브라우저 origin의 현재 로컬 장부 데이터에만 한정하고, 최종 확인 전에는 어떤 쓰기도 수행하지 않아야 한다. 사용자 정의 자금통은 삭제하지만 기본 자금통 7개는 같은 로컬 트랜잭션에서 다시 만든다. 원본 파일과 프로젝트 파일, 환경 변수, 원격 데이터는 절대로 대상이 아니다.

## 결정

- Settings에 삭제 대상과 비가역성을 설명하는 별도 초기화 영역과 재확인 dialog를 둔다.
- 취소, Escape, 배경 닫기는 데이터를 바꾸지 않고 dialog만 닫으며, 닫은 뒤 초기화 버튼으로 포커스를 복귀한다.
- 최종 확인은 하나의 IndexedDB 읽기·쓰기 트랜잭션에서 `transactions`, `importBatches`, `budgetSettlements`, `categoryRules`, `keywordCategoryRules`, `userSettings`, `budgetBuckets`를 비운다. 이어서 같은 트랜잭션에서 `budgetBuckets`에 `LIVING`, `IRREGULAR`, `EMERGENCY`, `SAVING`, `HOUSING_MARRIAGE`, `INVESTMENT`, `OTHER` 기본 레코드 7개를 다시 저장한다.
- 데이터베이스 이름과 스키마는 유지한다. 실패하면 UI는 dialog를 유지하고 일반화된 로컬 저장소 오류를 표시한다.

## 결정 이유

저장소 수준의 단일 transaction은 부분 초기화를 막으면서도 데이터베이스 삭제보다 범위가 좁고 예측 가능하다. UI의 두 단계 확인과 정확한 목록은 사용자가 선택 결과를 이해한 뒤에만 비가역 작업을 수행하게 한다.

## 고려한 대안

1. 즉시 초기화 버튼: 한 번의 오작동으로 금융 기록을 잃을 위험이 있어 제외했다.
2. IndexedDB 데이터베이스 삭제: 스키마 재생성·열린 연결 처리까지 포함해 실패 경계가 넓어져 제외했다.
3. 파일 시스템이나 `.env`까지 함께 삭제: 장부 초기화 범위를 넘고 사용자의 개발 환경을 훼손하므로 제외했다.

## 장점

- 사용자가 저장 범위와 비가역성을 확인할 수 있다.
- 저장소 초기화와 기본 자금통 재생성이 함께 성공하거나 실패해 부분적인 장부 삭제가 남지 않는다.
- local-first·무원격 전송 경계를 유지한다.

## 단점

- 삭제된 장부 데이터와 사용자 정의 자금통은 이 앱에서 복구할 수 없다. 기본 자금통 7개만 초기 상태로 다시 만들어진다.
- 브라우저 프로필 삭제, origin 변경, 다른 브라우저의 데이터에는 영향을 주지 않는다.

## 향후 다시 검토할 조건

사용자가 Import 이력과 규칙을 유지한 채 거래만 지우는 선택적 초기화, 내보내기·복원, 또는 암호화된 백업을 요구하면 별도의 범위·복구·보안 계약과 함께 재검토한다.
