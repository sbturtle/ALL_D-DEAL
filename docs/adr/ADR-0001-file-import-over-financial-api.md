# ADR-0001 금융 API 직접 연동보다 파일 Import 우선

- 날짜: 2026-08-05
- 관련 결정: [ADR-0002 local-first](ADR-0002-local-first-architecture.md), [ADR-0003 주 1회 Import](ADR-0003-weekly-import-instead-of-realtime.md)

## 상태

Accepted

## 최초 사용자 요구

금융기관 API에서 자신의 계좌와 카드 거래를 자동 조회하여 별도 수기 입력 없이 가계부를 만들고자 했다.

## 이후 대화에서 확인된 문제

대한민국에서 개인 개발자가 자신의 금융 정보를 공식 API로 자유롭게 호출하기 어렵다는 제약을 프로젝트 전제로 확인했다. API 연동에는 기관별 접근 권한, 인증, 운영 서버와 장기적인 유지보수도 필요할 수 있다.

## 변경된 요구사항

결정에 이른 흐름은 다음과 같다.

```text
금융 API 자동 연동
→ 한국 금융 API의 개인 접근 제약 확인
→ MyData/MyPDS 또는 금융기관 다운로드 파일 검토
→ 실시간 동기화가 필요하지 않음을 확인
→ 주 1회 File Import 방식으로 변경
```

## 결정

MVP는 사용자가 직접 내려받은 금융 파일을 가져오는 방식으로 개발한다. 목표 형식은 PDF, CSV, XLSX지만 한 번에 모두 지원하지 않으며, 먼저 Generic Test Format CSV로 파이프라인을 검증한 후 실제 마스킹 샘플을 근거로 Adapter를 하나씩 추가한다.

Import는 반드시 `Preview → Confirm → Commit` 순서를 거친다. 파일을 선택하는 즉시 영구 저장하지 않는다.

## 결정 이유

- 현재 사용자가 실제로 확보할 수 있는 데이터 전달 경로다.
- 계정 인증정보나 금융 API 접근 권한을 애플리케이션이 보유하지 않아도 된다.
- 기관별 차이를 Adapter 경계 안에 격리하면서 공통 가계부 기능을 먼저 검증할 수 있다.
- 주 1회 정리라는 사용 방식에는 수동 파일 선택의 비용이 허용 가능하다.

## 고려한 대안

### 금융기관 API 직접 연동

자동화 수준은 높지만 개인 접근 제약과 인증·서버 운영 복잡도가 현재 범위를 넘어선다.

### 화면 스크래핑 또는 비공식 자동화

형식 변경에 취약하고 보안 및 서비스 약관 위험을 키우므로 채택하지 않는다.

### 완전 수기 입력

구현은 단순하지만 반복 입력을 줄이려는 핵심 사용자 가치를 충족하지 못한다.

## 장점

- 구현 가능성이 높고 사용자가 원본 데이터 제공 시점을 통제한다.
- 금융기관별 파싱 문제를 독립적으로 진단할 수 있다.
- 인증정보 저장과 외부 통신을 최소화한다.

## 단점

- 사용자가 파일을 직접 내려받아야 한다.
- 기관마다 형식이 달라 Adapter 유지보수가 필요하다.
- 암호화되거나 스캔된 파일은 브라우저만으로 처리하기 어려울 수 있다.

## 향후 다시 검토할 조건

- 개인 개발자가 합법적이고 안정적으로 사용할 수 있는 공식 API가 제공된다.
- 수동 다운로드가 실제 사용에서 지속적인 이탈 원인으로 측정된다.
- 사용자 요구가 다중 사용자 또는 자동 동기화로 확장된다.
