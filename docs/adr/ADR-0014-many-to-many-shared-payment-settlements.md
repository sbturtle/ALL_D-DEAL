# ADR-0014 — 다대다 공동결제 정산

상태: Accepted
최초 결정일: 2026-08-10
관련 요구사항: FR-022, FR-023
선행 결정: [ADR-0005](ADR-0005-manual-shared-payment-settlements.md)

## 맥락

기존 공동결제 정산은 내가 먼저 결제한 출금 한 건과 여러 정산 입금을 연결하는 구조였다. 실제 생활에서는 한 번의 공동 구매가 여러 출금 거래로 나뉘거나, 여러 사람이 각각 입금해 정산하는 경우가 있어 단일 원결제 필드로는 하나의 비용 묶음을 표현할 수 없었다.

## 결정

- `BudgetSettlement`는 `outflowTransactionIds`와 `inflowTransactionIds` 두 배열을 저장한다. 두 배열은 각각 하나 이상이며 배열 안의 UUID는 고유해야 한다.
- 두 배열 사이에 같은 거래가 있으면 거부하고, 이미 다른 정산에 연결된 거래도 다시 연결하지 않는다. 한 거래는 최대 하나의 정산에만 참여한다.
- 저장 유스케이스는 모든 지출 참가자가 `OUTFLOW`, 모든 입금 참가자가 `INFLOW`인지 확인한다. 원본 `Transaction`은 변경하지 않는다.
- 선택 기간의 생활비는 일반 생활비에 더해, 해당 기간에 속한 연결 지출 합계에서 연결 입금 전체를 빼고 `max(순액, 0)`으로 반영한다. 입금 날짜가 이후여도 연결한 지출 기간에 귀속한다.
- IndexedDB 스키마 버전 5에서 v4의 `payerOutflowTransactionId`를 한 요소 배열로 바꾸고 `reimbursementInflowTransactionIds`를 `inflowTransactionIds`로 옮긴다. 기존 사용자의 정산을 잃지 않는 것이 우선이다.

## 결정 이유

다대다 배열은 분할된 결제와 여러 정산자를 원본 거래 그대로 묶으면서도, 정산 하나의 순지출을 명확하게 계산한다. 배열의 유일성과 단일 정산 참여 규칙은 같은 거래가 여러 번 차감되는 것을 막는다. 마이그레이션을 저장소 업그레이드에 포함하면 사용자가 별도 변환 작업을 하지 않아도 된다.

## 고려한 대안

1. 기존 단일 원결제 모델 유지: 분할 지출을 표현하지 못하므로 선택하지 않았다.
2. 공동결제용 합성 거래 생성: 원본 금액과 잔액이 중복 집계될 위험이 있어 선택하지 않았다.
3. 정산 관계를 별도 행 여러 개로 저장: 관계 제약과 삭제 일관성을 유지하기 어려워 현재 로컬 저장 규모에는 배열 모델이 더 단순하다.

## 장점

- 여러 지출과 여러 입금을 하나의 생활비 정산으로 관리한다.
- 원본 거래·잔액·일반 입출금 합계를 보존한다.
- 기존 v4 데이터가 자동으로 새 계약으로 변환된다.

## 단점과 제한

- 한 거래를 여러 정산에 나누어 배분할 수 없다.
- 자동 정산자 추정, 금액별 부분 배분, 외부 동기화는 제공하지 않는다.
- IndexedDB의 기존 필드는 마이그레이션 후 새 배열 필드로 저장된다.

## 재검토 조건

부분 금액 배분이나 한 거래의 여러 목적 귀속이 실제 요구로 확인되면 정산 관계를 별도 엔터티로 분리할지 다시 검토한다.
